# Evidence Measurement Plan

**対象:** SES営業交流会サイト / Recruitment Insight / MatchPilot  
**目的:** 今後「改善した」と説明するために、対象者・期間・件数・方法・Before / After・限界を記録する。  
**位置づけ:** 測定開始前の計画。ここに記載する成功基準や指標は実績ではない。

## 1. 共通測定原則

### 1.1 測定前に定義すること

各検証では、開始前に次の14項目を記録する。

1. 改善したい状態
2. 利用者
3. 測定する業務・タスク
4. Beforeの方法と状態
5. Afterの方法と状態
6. 計測・観察方法
7. 対象件数
8. 測定期間
9. 成功基準
10. 失敗・悪化の基準
11. 定性評価
12. 例外と除外条件
13. 自分の担当範囲
14. 未確認事項

Beforeの記録がない場合は、記憶から数値を作らず「Before未計測」とする。その場合、最初の2〜3回を基準値の取得期間にし、以後の同条件の結果と比較する。

### 1.2 区別する評価

| 評価 | 意味 | 証拠として必要なもの |
|---|---|---|
| 時間削減 | 同じ業務の実作業時間が短くなった | 同じ起点・終点で測ったBefore / After |
| コスト削減 | 実際の支出が減った | 対象費目、金額、比較期間 |
| 使いやすさ | 利用者の主観評価 | 質問、回答者、尺度、自由記述 |
| 継続利用 | 同じ利用者が繰り返し使った | 利用者、期間、利用機会、実利用回数 |
| 業務成果 | 採用・営業・運営の指標が変わった | 指標定義、件数、期間、比較条件、外部要因 |

時間が短くなっても人件費や外注費が変わらなければ、コスト削減とは表現しない。使いやすいという回答だけで、業務成果が改善したとは表現しない。

### 1.3 記録ルール

- 時間は計測開始・終了条件を固定し、分単位で記録する。
- 件数は母数も残す。例として「手動修正1件」だけでなく「申込30件中1件」と記録する。
- 成功と失敗の両方を残し、都合のよい回だけを選ばない。
- 障害、通信不良、入力ミス、特殊案件などは例外欄へ残し、除外時は理由を書く。
- 個人名、企業名、連絡先などの機密情報は測定表に記載しない。利用者は匿名IDで管理する。
- 自作ツール以外の運用変更や慣れの影響を、ツールの効果に含めない。
- 測定中に見つかった機能案は「Next Improvement」に記録し、この計画内では実装しない。

## 2. SES営業交流会サイト

### 2.1 測定目的と利用者

改善したいのは、申込受付からキャンセル後の残席復元、当日確認までを一つの運用として安定させること。主な利用者は運営者である自分で、参加者は申込・メール受信・キャンセルの各接点を利用する。

対象業務は、申込管理、定員確認、受付連絡、キャンセル処理、残席確認、問い合わせ対応、当日受付確認とする。

### 2.2 Before

サイト導入前の記録が確認できる場合だけ、次を過去のメール、申込表、カレンダー、作業記録から復元する。

- 申込受付方法と定員確認方法
- メール送信とキャンセル処理の方法
- 手動修正、問い合わせ、例外対応の件数
- 申込管理と当日準備に要した時間

過去の開始・終了時刻や件数を確認できない項目は「Before未計測」とする。記憶による所要時間は参考コメントに分け、比較値に使わない。

### 2.3 Afterと測定項目

今後の開催ごとに、次を1行または集計行として記録する。

開催条件は既存テンプレートのDate（開催日）、Case（開催回）、User（運営者ID）、Comment（開催規模、申込受付期間、開催形態、運営人数）に固定ラベルで記録する。条件を独立した列にはせず、件数・時間の比較時に必ず併記する。

| 指標 | 定義・数え方 | 取得方法 |
|---|---|---|
| 申込件数 | 有効な申込の総数 | 申込データを開催終了後に集計 |
| キャンセル件数 | 受理したキャンセル数 | キャンセル記録を集計 |
| 残席復元件数 | キャンセル後に残席が戻った件数 | 申込・キャンセル記録を照合 |
| 手動修正件数 | データ、定員、状態を人が修正した回数 | 修正時に理由とともに記録 |
| 問い合わせ件数 | 申込・受付メール・キャンセル・残席に関する問い合わせ | 内容を分類して件数のみ記録 |
| 受付メール修正件数 | 誤記、未達、再送などで手作業が必要だった件数 | メール対応時に記録 |
| 例外対応件数 | 通常フロー外の判断・操作が発生した件数 | 例外の種類と対応時間を記録 |
| 申込管理時間 | 申込確認から管理表の状態確認までの実作業時間 | 作業開始・終了をタイマー記録 |
| 運営準備時間 | 参加者確認など、対象として定めた事前準備の実作業時間 | 対象作業を先に固定して計測 |
| 当日確認時間 | 受付開始から対象者確認完了までの作業時間 | 当日の開始・終了時刻を記録 |

### 2.4 対象件数・期間

- 最初の2〜3開催を基準値取得期間とする。
- 各開催の全申込を対象にし、除外した申込があれば理由を残す。
- 開催規模、告知期間、定員、担当者数が大きく異なる回は、単純比較せず条件を併記する。
- 可能なら基準値取得後も3開催以上を測り、単発の変化で結論を出さない。

### 2.5 成功・失敗基準

基準値取得前に改善率を固定しない。2〜3開催の測定後、中央値と例外の種類を確認して、次の比較期間の数値基準を決める。

成功候補は、同程度の申込数・運営条件で、管理時間、手動修正率、問い合わせ率、例外対応率のいずれかが基準期間より改善し、他の重要指標が悪化していない状態とする。残席復元は、対象となるキャンセルで正しく復元された割合を確認する。

失敗・悪化は、誤った定員状態、申込やキャンセルの取りこぼし、メール対応の増加、手動修正率または作業時間の継続的増加が見られる状態とする。

### 2.6 定性評価・例外・担当範囲

開催後に運営者として「迷った操作」「確認に時間がかかった箇所」「通常フローで処理できなかったこと」を記録する。問い合わせ本文や個人情報は保存せず、分類と件数だけ残す。

通信障害、参加者の重複入力、締切後の個別申込、運営都合による定員変更は例外として分離する。自分の担当範囲は、業務整理、サイト・運用設計、実装、運営、計測、改善判断である。

未確認事項は、サイト導入前の比較可能な記録の有無、受付メールの到達確認方法、当日確認時間の起点・終点、他の運営者が参加する場合の担当分担である。

## 3. Recruitment Insight

### 3.1 測定目的と利用者

採用担当者が、候補者・求人・企業・選考の情報から、停滞箇所と次の対応を正しく特定できるかを検証する。見た目の好みだけを成功基準にしない。

採用担当、人材紹介担当、SES採用担当、営業兼採用担当から、まず3名以上を目安にする。実顧客情報は使わず、全員が同じサンプルデータを使う。実務経験、普段の管理方法、対象画面の事前利用経験を記録する。

### 3.2 Before / After比較

可能なら、同じ情報を偏りのないSpreadsheetとRecruitment Insightに用意し、同じ5タスクを実施する。順番による学習効果を抑えるため、利用者ごとに先に使う方法を入れ替える。

Beforeは普段の管理方法、または比較用Spreadsheet。AfterはRecruitment Insightとする。比較用Spreadsheetに不自然な分割、隠し項目、読みにくい装飾を入れない。普段の管理方法と比較用データが異なる場合は、その限界を記録する。

### 3.3 タスクテスト

利用者には操作方法を先に教えず、タスクの目的だけを提示する。

1. 現在、どの選考段階が停滞しているか確認する。
2. 次に対応すべき候補者を探す。
3. 主な離脱理由を確認する。
4. 指定した求人の選考状況を確認する。
5. 次回アクションが必要な対象を確認する。

各タスクについて、正答、開始から回答までの時間、迷い、質問、誤った選択、クリック数を観察する。正答と許容範囲はテスト前に回答表へ定義する。

### 3.4 測定項目

| 指標 | 定義 |
|---|---|
| タスク成功率 | 正しく完了したタスク数 ÷ 実施タスク数 |
| 完了時間 | タスク提示から最終回答まで |
| 迷った回数 | 戻る、同じ画面を往復する、一定時間操作が止まるなど、事前定義した行動数 |
| 質問回数 | 進め方や用語についてテスト担当者へ質問した回数 |
| 誤判断数 | 事前に定義した正答・許容範囲から外れた回答数 |
| クリック数 | タスク開始から回答までの操作数 |
| 初見理解度 | 5段階評価と理由 |
| 情報量 | 少なすぎる／適切／多すぎるの選択と理由 |
| 情報不足 | 欲しかったが表示されていない情報の自由記述 |

画面録画は本人の同意を得られる場合だけ行う。同意がない場合は観察者が時刻と行動を記録する。

### 3.5 対象件数・期間と判定

- 初回は3名以上、各5タスクを実施する。
- 初回で見つかった問題を整理した後、別の3名以上で再検証する。
- 少人数のため、平均値だけでなく各人の結果を併記する。

初回の成功基準は、各タスクの正答条件を満たせること、重大な誤判断につながる表示がないこと、次の対応を回答できることとする。Spreadsheet比較を行う場合は、正答率を優先し、完了時間・迷い・主観評価を併記する。

失敗・悪化は、重要タスクを完了できない、誤った対象を選ぶ、比較方法より誤判断が増える、情報量が原因で次の対応を決められない状態とする。3名の結果だけで一般的な採用成果を主張しない。

### 3.6 定性質問・例外・担当範囲

共通ヒアリングに加えて、次を聞く。

- 最初に理解できた情報は何か。
- 採用業務で使うなら、判断に必要な情報は何か。
- 次の行動を決めやすかったか。その理由は何か。
- 普段の管理方法と比べて、判断しやすい点・しにくい点は何か。

採用経験がない利用者、データ内容をすでに知っている利用者、途中で説明を受けたタスクは区別して記録する。自分の担当範囲は、課題・タスク・サンプルデータ・画面構造・測定方法の設計、観察、結果整理である。

未確認事項は、他者による利用実績、比較用Spreadsheet、正答表、用語理解の差、画面録画への同意である。

### 3.7 現時点で測らない項目

正式導入前のDemoであるため、採用率、内定率、定着率、採用単価、候補者品質、AI合否精度は測定対象にしない。利用者テストの結果を、これらの採用成果へ読み替えない。

## 4. MatchPilot

### 4.1 測定目的と利用者

KPI・接点・関係値・NG理由・次回アクションという管理項目が、実際の営業運用で無理なく更新され、次のフォロー判断に使えるかを検証する。

最初に自分で測定し、可能なら自分以外の利用者1名以上で試す。自己利用だけの場合は「他者利用未検証」と明記する。他者の営業データを使う場合は、所属組織の許可と匿名化方法を先に確認する。

### 4.2 自作前提にしない比較

検証前に、現在のCRMまたはSpreadsheetで、同じ管理項目とタスクを扱えるかを確認する。既存ツールの設定変更や運用ルールで解決できる場合は、それも有効な結果とする。

比較する場合は、現在の管理方法とMatchPilotで、対象企業数、更新頻度、利用期間をそろえる。二重入力による追加時間と入力漏れを独立して記録し、MatchPilot固有の負担と混同しない。

### 4.3 測定項目

| 指標 | 定義・取得方法 |
|---|---|
| 入力時間 | 1回の更新開始から保存完了までの時間 |
| 1社更新時間 | 対象企業1社の必要項目を更新する時間 |
| 更新継続率 | 更新予定回数に対して期限内に更新した回数の割合 |
| 未更新件数 | 更新期限を過ぎた対象数 |
| フォロー漏れ | 期限までに必要な接触を行えなかった対象数。後から判明した根拠も残す |
| 次回アクション設定率 | 接点更新後に次回アクションと期限が設定された割合 |
| NG理由入力率 | NGとなった対象のうち理由が記録された割合 |
| 会議参照回数 | 定例や確認会で実際に画面を参照した回数 |
| 他者理解 | 他者が指定企業の状況・理由・次の行動を説明できたか |

### 4.4 対象件数・期間

- 自己利用は、実在する管理対象を匿名IDに置き換え、まず2〜4週間測定する。
- 対象企業数、予定更新回数、実更新回数を記録する。
- 他者テストでは、本人が担当していない3〜5件を見て状況と次の行動を説明してもらう。
- 比較期間に案件量や休暇などの差がある場合は条件として残す。

### 4.5 成功・失敗基準

機能が動くことは成功に含めない。測定前に更新予定を定義し、期間終了後に次を確認する。

成功候補は、必要な更新が継続できる、期限超過やフォロー漏れを発見できる、次回アクションが記録される、他者が状況を説明できる状態である。既存CRMやSpreadsheetと同等以下の入力負担であることも確認する。

失敗・悪化は、二重入力を除いても更新が続かない、入力時間が増える、管理項目の意味が伝わらない、誤ったフォロー判断が生じる、既存ツールで同じ目的を十分達成できるのに保守負担だけが増える状態とする。

### 4.6 定性評価・例外・担当範囲

利用後に、入力を後回しにした理由、不要な項目、足りない情報、会議で見たい情報、既存方法へ戻った場面を聞く。

急な案件停止、担当変更、長期休暇、データ移行、並行運用による二重入力は例外・影響要因として記録する。自分の担当範囲は、業務項目・Prototype・比較・測定の設計と、自己利用範囲の入力・観察である。

未確認事項は、他者が継続利用できるか、実際の入力負担、既存CRMとの差、チーム会議で利用できるか、営業成果への影響である。

## 6. 定性ヒアリングテンプレート

1. 何が一番分かりやすかったですか。
2. どこで迷いましたか。
3. 今の方法より良い点は何ですか。
4. 今の方法より悪い点は何ですか。
5. 不要な機能・情報はありますか。
6. 不足している機能・情報はありますか。
7. 継続して使いたいですか。
8. その理由は何ですか。
9. 実務導入する場合に不安な点は何ですか。
10. 最初に改善してほしい点は何ですか。

回答は要約だけでなく、匿名化した原文または意味を変えない記録も残す。誘導を避けるため、評価理由を先に説明せず質問する。

## 7. Evidence Level

| Level | 判定条件 |
|---:|---|
| 0 | 自分で作っただけ。利用による検証は未確認 |
| 1 | 自分が実業務または想定タスクで使った |
| 2 | 自分以外の人が定めたタスクを試した |
| 3 | 自分以外の人が、定めた期間・機会で継続利用した |
| 4 | 対象者・期間・件数・条件を示したBefore / Afterで業務指標が変わった |
| 5 | 複数人・複数業務または複数期間で同様の変化を再現した |

公開URLがある、機能が動く、感想を一度もらった、という事実だけではLevelを上げない。Level 4以上では、使いやすさだけでなく、定義した業務指標の変化と限界を示す。

### 現時点の仮分類

| 事例 | 仮Level | 確認済みの根拠 | Levelを上げるために必要な確認 |
|---|---:|---|---|
| SES営業交流会サイト | 1 | 自分が主催する交流会で開催ごとに実運用・改善している | 他の運営者の利用範囲、開催単位の測定記録、比較可能なBefore / After |
| Recruitment Insight | 0 | 公開Demoと画面構造はあるが、他者テストは未確認 | 定めたタスクによる他者テスト。継続利用とは分ける |
| MatchPilot | 0 | Prototypeはあるが、自己利用・他者利用の範囲は未確認 | 自己利用記録。その後、他者テストと継続利用記録 |

分類は現時点で確認できる証拠に限定した暫定値とし、検証記録を確認した時点で更新する。

## 8. Portfolioへ反映する条件

測定結果をPortfolioの成果表現へ追加する前に、次を説明できる状態にする。

- 対象者と自分との関係
- 測定期間
- 対象件数と母数
- 指標の定義と測定方法
- 比較可能なBeforeとAfter
- 成功例だけでなく、例外、悪化、未確認事項
- 自分の担当範囲

Beforeがない場合はBefore / After改善と表現せず、Afterの運用実績または利用者テスト結果として掲載する。少人数のテスト結果を一般的な業務成果へ広げない。

## 9. 実行優先順位

1. **SES営業交流会サイト:** 次回開催から測定表を使う。実運用中で、開催単位の件数・例外・時間を最も早く記録できる。
2. **Recruitment Insight:** 同じサンプルデータと5タスクを準備し、採用実務経験者3名以上で初見テストを行う。
3. **MatchPilot:** 現在の管理方法で足りない点を先に確認し、自己利用を2〜4週間記録する。その後、他者利用を検討する。
