# SES営業交流会 Measurement Runbook

目的：

次回開催を最初の正式実測回として、開催条件・運用件数・手動対応・例外・作業時間を同じ基準で記録する。

このRunbookは「どう記録するか（手順）」を定義する。実測値そのものは記録しない。実測値は `docs/ses-meetup-evidence-log.md` へ記録する。

重要：

- 後から推測しない。
- その場で取れる情報はその場で記録する。
- `0件`と`未計測`を区別する。
- Evidence Sourceを残す。
- 良い結果だけを記録しない。問題・例外・悪化も残す。
- 実測のために通常運用を不自然に変えない。

## 関連文書

| 文書 | 役割 |
|---|---|
| `docs/evidence-measurement-plan.md` | 測定原則・Before / After・Evidence Level・Portfolio反映条件の定義（計画） |
| `docs/ses-meetup-evidence-log.md` | 開催単位の実測値の記録先（Evidence Log） |
| `docs/ses-meetup-measurement-runbook.md` | 開催前・中・後のどのタイミングで何を記録するかの手順（本書） |

本書は上記2文書の定義（Evidence Level、Before / After、Evidence Source、手動対応、例外、時間測定、Portfolio反映条件）と矛盾させない。矛盾が見つかった場合は、本書側を勝手に修正せず、作業を停止して報告する。

## 記録禁止事項

以下は本Runbook・Evidence Logのいずれにも記録しない。

- 氏名
- メールアドレス
- 電話番号
- 個人を特定できる問い合わせ本文
- 非公開の企業情報・秘密情報

問い合わせは「カテゴリ」と、必要なら意味を変えない短い要約のみ記録する。

# フェーズ構成

Runbookは開催サイクルを4段階に分ける。

| 段階 | 区間 |
|---|---|
| A | 開催前 |
| B | 申込受付期間中 |
| C | 開催当日 |
| D | 開催後 |

---

# A. 開催前

## A-1. 開催条件の確定

開催前に、次の項目を確定して Evidence Log の「開催情報」「開催条件メモ」へ記録する。

- 開催日
- 回次
- 開催形態
- 会場
- 想定定員
- 申込受付開始日
- 申込受付終了予定日
- 運営人数
- 記録者
- Evidence Source候補

Evidence Source候補：

- Spreadsheet集計
- キャンセル履歴
- 問い合わせ集計
- 手動タイムログ
- システム動作確認

現時点で確定できない項目は空欄にせず「未確認」とする。

## A-2. システム動作確認

開催前に次の項目を確認し、`正常` / `問題あり` / `未確認` のいずれかで記録する。

- 申込フォーム
- 定員管理
- 受付メール
- キャンセル
- 残席復元
- Spreadsheet連携

`問題あり`の場合は、あわせて次を記録する。

- 内容
- 対応
- 実測への影響

## A-3. 時間測定方法の決定

開催前に、時間測定の方法を1つに決めておく。

推奨：

1. 作業開始時に時刻を記録する。
2. 作業終了時に時刻を記録する。

または、タイマーを使用する。

後から「たぶん20分」のように推定して記録することは禁止する。

## A-4. タイムログ対象

最低限、次の作業を測定対象とする。

- 申込管理
- 問い合わせ対応
- キャンセル対応
- サイト / データ修正
- 事前受付確認
- 当日受付確認
- 事後処理

交流会そのものの開催時間、集客・営業・SNS活動は運用時間に含めない。サイト・申込運用と直接関係する場合だけ、対象に含めた理由を記録する。

---

# B. 申込受付期間中

毎日記録する必要はない。事象が発生したタイミングで記録する。

記録対象：

- 新規申込
- キャンセル
- 重複申込
- 無効申込
- 手動修正
- 問い合わせ
- 例外
- システム不具合

## B-1. 申込件数

可能な限りSpreadsheet等の一次情報から取得する。手計算だけに依存しない。

記録：

- 総申込数
- 有効申込数
- キャンセル数
- 残席復元数

分母が確認できない率は計算せず「未計測」とする。

## B-2. キャンセル

キャンセル発生時に次を確認・記録する。

- キャンセル処理が正常だったか
- 残席が復元されたか
- 手動対応が必要だったか
- メール対応が必要だったか
- 例外だったか

Evidence Source：キャンセル履歴 / Spreadsheet / システム確認

## B-3. 手動対応

手動対応が発生した時点で記録する。

- 日時
- 種類
- なぜ必要だったか
- 対応内容
- 所要時間
- 再発可能性

個人情報は書かない。

## B-4. 問い合わせ

問い合わせ発生時に、カテゴリのみ記録する。

- 申込方法
- 受付確認
- キャンセル
- 会場
- 支払い
- その他

必要なら意味を変えない短い要約を添える。個人を特定できる本文は記録しない。

## B-5. 例外

例外発生時に、次のいずれかを仮分類する。

- システム起因
- 運用起因
- 利用者起因
- 未分類

分類は後で変更してよい。

## B-6. 改善案が浮かんだ場合

その場で実装しない。次だけを記録する。

- 改善案
- 発生理由
- 緊急度
- 次回までに必要か
- 作らずに対応可能か

Phase 51では測定を優先する。

---

# C. 開催当日

## C-1. 当日の確認項目

- 最終申込数
- 有効申込数
- キャンセル数
- 当日参加人数
- 当日キャンセル
- 無断欠席を記録する場合の扱い
- 受付確認時間
- 手動照合の有無
- 受付時例外

## C-2. 当日受付

記録：

- システム / Spreadsheet確認で完結した件
- 手動確認が必要だった件
- 名前照合以外の追加対応件数
- 受付時問い合わせ
- 当日修正

個人名は記録しない。

## C-3. 実参加人数

可能な限り、当日確認した実数を使用する。推定は禁止する。

後日修正する場合は「修正理由」を残す。

## C-4. 当日の時間測定

- 受付準備開始 / 終了
- 当日確認開始 / 終了
- 事後処理開始 / 終了

交流会そのものの開催時間は運用時間に含めない。

---

# D. 開催後

開催後、可能なら24〜48時間以内に記録を確定する。時間が経つほど手動対応や例外を忘れるため。

## D-1. 開催後集計

次を確定する。

- 総申込数
- 有効申込数
- キャンセル数
- 実参加人数
- 手動修正件数
- 問い合わせ件数
- 例外件数
- 各作業時間
- 合計運営作業時間

## D-2. Evidence Source確定

各主要数値について、取得元を確認して記録する。

| 数値 | Evidence Source（例） |
|---|---|
| 申込数 | Spreadsheet |
| キャンセル | キャンセル履歴 |
| 問い合わせ | 問い合わせ集計 |
| 時間 | タイムログ |
| システム状態 | 動作確認 |

取得できない項目は「未確認」とする。

## D-3. 0件 / 未計測 QA

開催後に必ず確認する。

- `0件` ＝ 確認した結果、発生しなかった。
- `未計測` ＝ その値を記録していない。

この2つを混同しない。

## D-4. 正規化指標

分子・分母が揃っている場合だけ算出する。

- 問い合わせ率
- 手動修正率
- 例外率
- 1申込あたり管理時間

初回実測でも計算可能なら記録してよい。ただし初回だけで改善効果とは判断しない。

## D-5. 開催後レビュー

次に回答する。

- 最も手間がかかった作業
- 最も多かった例外
- 問い合わせが多かった内容
- システムで完結した範囲
- 手動で残った範囲
- 不具合
- 作らない判断
- 次回改善候補

## D-6. 改善案分類

開催後、改善候補を次へ分類する。

| 区分 | 意味 |
|---|---|
| A | 次回までに対応必須 |
| B | 効果を確認してから判断 |
| C | 既存運用で十分 |
| D | 不要 |

Phase 51では実装しない。

## D-7. 作らない判断レビュー

改善候補ごとに「本当に開発が必要か」を確認する。

代替手段：

- 運用ルール
- Spreadsheet
- メール文
- チェックリスト
- 手動確認
- 既存SaaS

これらで十分なら「作らない判断」として記録する。

## D-8. Evidence Level判定

- 初回測定後も、原則 Level 1。
- ログを詳細に取っただけでは Level を上げない。
- Level 2以上には、他者利用のEvidenceが必要。
- Level 4には、Before / Afterの業務指標変化が必要。

（Level定義は `docs/evidence-measurement-plan.md` および `docs/ses-meetup-evidence-log.md` に従う。）

# 初回測定の位置付け

初回は **Baseline取得** として扱う。

目的は、良い数字を出すことではなく、今後比較できる基準値を作ること。

## 比較禁止事項

初回終了後に、次の表現は使わない。

- 「改善した」
- 「効率化した」
- 「工数削減した」

少なくとも2〜3開催分を蓄積し、開催条件も併せて比較する。

## Portfolio更新禁止

初回実測後も、自動的にPortfolioを変更しない。Portfolioへの反映は、`docs/evidence-measurement-plan.md` および `docs/ses-meetup-evidence-log.md` で定義した条件を満たしてから検討する。

# Runbook / Evidence Log の役割分離

| 文書 | 内容 |
|---|---|
| Runbook（本書） | 手順。実測数値は蓄積しない。 |
| Evidence Log（`docs/ses-meetup-evidence-log.md`） | 実測値。開催単位で記録する。 |

正式な実測値は Evidence Log へ記録する。Runbook側には実測数値を蓄積しない。
