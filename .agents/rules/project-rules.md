# satochan-portfolio プロジェクト固有ルール

このドキュメントは、グローバルルール（`GEMINI.md`）を補完し、公開中のポートフォリオサイト（`satochan-portfolio`）を安全に運用・改善するためのプロジェクト固有ルールです。

---

## 1. サイトの目的と位置づけ（最重要）

本サイトは、単なるエンジニアの作品集や制作物ギャラリーではありません。

**「SES営業・採用の現場経験をベースに、AI活用・業務改善・ツール実装までできることを伝える営業資産」**

以下の軸を常に一体として扱い、どれか1つだけの専門サイト（例：「AIエンジニア」「フルスタック開発者」単体）へ勝手に再構成・再定義しないでください。

- **SES営業**: 提案・商談・BP開拓・営業マネジメント・0→1立ち上げ
- **採用**: 母集団形成・面談/面接・選考基準標準化・入社後フォロー
- **AI活用**: 業務フロー棚卸し・判断工程とAIの切り分け・ナレッジ活用
- **業務改善**: 属人化解消・業務標準化・KPI設計・運用フロー設計
- **ツール開発・実装**: 課題解決に必要な範囲でのプロトタイプ/MVP/Webツール実装

---

## 2. コンテンツの正本（Single Source of Truth）

公開情報の正本は `src/content/` 配下の TypeScript ファイルです。コンポーネント内への事実情報のハードコードは禁止します。

- `src/content/site.ts`: サイト基本情報、Hero、Proof（実績数値）、Contact、ナビゲーション
- `src/content/works.ts`: Selected Works、Supporting Projects、技術スタック、ステータス
- `src/content/services.ts`: 提供サービス、相談内容（What I Do / Consultation / Use Cases）
- `src/content/caseStudies.ts`: 詳細事例（Problem → Approach → Solution → Impact）

---

## 3. 実績・経歴・数値の事実性（Factuality）

- **推測・誇張の禁止**: 経歴、年数、役職、実績、Skill数、資格、案件、制作物等を推測で追加・変更しない。
- **根拠のない成果表現の禁止**: 「導入実績」「売上向上」「○%改善」等の未確認・未実測の成果表現を追加しない。
- **概算値の扱い**: 概算値を掲載する場合は、その前提と根拠が分かる注記（`footnote`等）を必ず維持する。
- **非公開情報の厳守**: 取引先企業名、担当者名、単価、契約条件、商流、営業記録の原文は一切掲載しない。
- **脚色の禁止**: AIが内容を良く見せる目的で事実を脚色・美化しない。

---

## 4. デザイン品質と一貫性

- **AIテンプレート感の排除**: 均一なカード配置、不要なカード増設、無秩序なグラデーション/光彩/過度な角丸/過剰なアイコンの追加を行わない。
- **視覚的階層と余白**: 見出し・余白・タイポグラフィ・レイアウトに明確な階層を持たせ、情報量が多くても視線誘導と余白を最優先する。
- **デザイン判断基準**: 「見栄え」だけでなく、「読み手（事業責任者・採用担当者・案件発注者）が本人の強みと実務価値を直感的に理解できるか」を基準とする。
- **既存設計の尊重**: 既存のトーン＆マナー（白・薄青サーフェス・Deep Navyの引き締め、洗練されたフォント・余白設計）を尊重し、全面的なデザイン変更を勝手に行わない。

---

## 5. コンテンツの意味・文脈の維持

文章のリライトや要約時も、以下を勝手に変更しないこと。

- 本人の実体験および経験年数
- 得意領域および対応可能な提供範囲
- 実際に行ったこと（課題・アプローチ・解決策・変化）
- 制作物・プロトタイプの位置づけ（完成品と試作品の区別）
- 「見栄えを整える表現調整」と「事実の改変」を厳格に区別する。

---

## 6. Business Skills / AI Workflow の位置づけ

- 「AIツールが使える」という単なる道具の列挙に後退させない。
- **「現場知識・業務手順・判断基準を、AIが再利用可能な仕組み・Skill・Workflowへ落とし込める」** という実務価値が伝わる構成を維持する。
- 一時的なモデル名やサービス名に依存させず、業務プロセス（Research → Think → Build → Verify → Operate → Improve）と判断基準を体系化している価値を伝える。

---

## 7. 制作物・プロジェクトの扱い

- **実在性の担保**: 実際に存在し、実装で確認できたもののみを掲載する。
- **ステータスの正直な明記**:
  - `Live / Production`: 実際に公開・運用されているもの（例: SES営業交流会 申込サイト）
  - `Prototype / In Development`: 開発中・プロトタイプ（例: MatchPilot）
  - `Speaking`: 登壇・セミナー実績（例: AI活用ミニ講座）
  - `Personal`: 個人運用の仕組み（例: Obsidian × AI ナレッジ活用）
  - `Demo`: 公開デモ（例: MatchHire）
- **未実装機能の誇張禁止**: 開発途中のものを完成済みと表現したり、実装していない機能を「実装済み」と書かない。
- **技術スタックの正確性**: 各リポジトリの実装で確認できた技術のみを掲載し、推測で技術名を追加しない。

---

## 8. 外部リンク・Contact導線の安全性

- **推測URLの禁止**: GitHub URL、デモURL、公開サイトURLを推測で作成・変更・削除しない。
- **連絡先チャネルの保護**:
  - 現在コード上で確認されている公開外部リンクは GitHub のみ。
  - メールやX（旧Twitter）など、公開先が未確定の連絡手段を推測で追加しない。`src/content/site.ts` の `contactChannels` の null 運用（確定するまで null を維持する設計）を勝手に埋めない。
- **Formspree / 問い合わせフォーム**:
  - `FORMSPREE_FORM_ID` などの環境変数・識別子はサーバー側（Route Handler）専用として扱い、クライアント側へ露出させない。
  - ハニーポット、サーバーサイドバリデーション、タイムアウト/エラーハンドリングを維持する。

---

## 9. レスポンシブ・モバイルUX

PC表示だけでなく、モバイル（スマートフォン・タブレット）での挙動を必ず考慮・検証する。

- 横スクロール（水平はみ出し）が発生しないこと
- 見出しや長いテキストが不自然に折り返されないこと
- カードやボタンのタップ領域が狭くなりすぎないこと
- 画像がコンテナをはみ出さないこと
- CTAボタンや外部リンクが誤操作なくタップできること
- モバイル表示時に情報密度が高すぎて視認性を損なわないこと

---

## 10. 画像・アセットの安全性

- 既存の画像アセットを勝手に削除しない。
- 低品質なダミー画像や無関係なストック画像へ差し替えない。
- 実績と誤認されるような無関係なイメージ画像を追加しない。
- 画像を追加・差し替える際は、取引先企業名、個人名、営業データ、機密情報が含まれていないか（または適切にマスキングされているか）を確認する。

---

## 11. SEO / メタデータ

- `title`, `description`, `OGP`, `robots`, `sitemap`, `canonical` 等の既存設定を理由なく変更しない。
- `src/content/site.ts` の `getSiteUrl()` による null ガード構造を維持する（本番URL未確定時に架空URLを出力・ハードコードしない）。
- SEO改善を口実に、実態と異なるキーワードや誇張表現をメタデータに追加しない。

---

## 12. 公開中サイトとしての運用ルール

本サイトは、実際の営業・採用・副業活動に利用されている公開中サイトです。

- 実験的な変更を無断で本番反映しない。
- 大規模なUI再設計やリファクタリングを一度に行わず、変更は小さく分割する。
- 既存の正常な導線（ページ内リンク、問い合わせ、外部リンク）を壊さない。
- 改修時は既存の表示・動作との比較・整合性を維持する。
- DB・CMS・認証・アニメーションライブラリ等の不要な新規外部依存を追加しない。

---

## 13. 実装・検証コマンド

コード変更時は、`package.json` に定義された正式なコマンドのみを使用する。

- **Lint**: `npm run lint`
- **Typecheck**: `npm run typecheck`
- **Build**: `npm run build`
- **Git差分検証**: `git diff --check`

※ 存在しないコマンドを推測して実行しないこと。

---

## 14. Git・デプロイ・インフラ操作の規律

- 既存の未コミット変更を消さない。
- 作業対象外のファイルを stage / commit しない。
- ユーザーからの明示的な指示がない限り、`commit`, `push`, `deploy` を実行しない。
- `git reset --hard`, `git rebase`, `git commit --amend`, `git push --force` 等の破壊的操作は絶対に行わない。
- Vercel のプロジェクト設定や環境変数を勝手に変更しない。
